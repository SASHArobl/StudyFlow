# StudyFlow — техническая архитектура

Status: **Approved 1.0**. Requirements, architecture, design system, references, and implementation roadmap are approved. Stage 4 initialization is authorized; see docs/development.md for the installed foundation. No application schema or hosted infrastructure has been created.

## 1. Общая архитектура

Одно приложение Next.js и один управляемый проект Supabase. В браузере — рабочая копия данных в IndexedDB; в Postgres — подтверждённые данные аккаунта. Интерфейс читает локальную копию, изменения записываются вместе с очередью отправки. Сервер проверяет права, версии и ограничения перед синхронизацией.

Это необходимо для FR-08: офлайн включает редактирование, Focus и повторное открытие приложения. Серверные формы и кэш HTTP-ответов этого не обеспечивают. Цена решения — протокол синхронизации и миграции локальной БД.

| Часть | Ответственность |
| --- | --- |
| React UI | Отображение, формы, доступность, локальное состояние интерфейса |
| Предметные функции TypeScript | Учебные правила, статусы, расчёт интервалов и аналитики; без React, сети и хранения |
| IndexedDB / Dexie | Локальные записи, очередь, конфликты, восстановление Focus |
| Next.js Route Handlers | Auth, проверка HTTP/JSON, вызов транзакционных функций Postgres |
| Postgres | Права, связи, версии, идемпотентность, атомарность, конфликты, блокировка Focus |
| Supabase Auth | Пароли, подтверждение email, вход, восстановление и сессии |
| Service worker | Общая оболочка и статические ресурсы; не персональные API-ответы |

Предметные функции импортируются непосредственно. Нет repositories, базовых service-классов, DI, фабрик, отдельного backend-приложения или брокера сообщений. Небольшие функции локальной записи и синхронизации нужны из-за реальных границ хранения и сети.

## 2. Стек и альтернативы

| Выбор | Почему подходит | Альтернатива и компромисс |
| --- | --- | --- |
| Next.js App Router + React + strict TypeScript | Один проект для UI, auth и HTTP; соответствует предпочтению владельца | Vite SPA проще для офлайна, но серверные операции нужно размещать иначе. Next выбран с клиентской рабочей областью, без персонального SSR |
| Tailwind CSS + выборочные shadcn/ui primitives | Управляемые токены и базовые доступные взаимодействия без dashboard-шаблона | Большая UI-библиотека сильнее ограничивает дизайн; полностью свои диалоги/меню увеличивают риск ошибок доступности |
| Supabase Postgres + Auth | Связи, транзакции, RLS и password auth в одном сервисе | Firebase даёт готовый offline CRUD, но менее естественен для реляционных правил. Отдельные Postgres и auth-провайдер добавляют интеграции |
| Supabase JS + @supabase/ssr | Официальная интеграция auth и cookie-сессий | Своя авторизация добавляет ненужную ответственность за пароли |
| Dexie + dexie-react-hooks | Индексируемая локальная БД, транзакции, наблюдаемые React-запросы | Нативный IndexedDB требует больше кода; localStorage не подходит для связанных транзакционных данных. Dexie Cloud не используется |
| Zod | TypeScript-контракты форм и HTTP с проверкой JSON | Только TypeScript не проверяет входные данные во время исполнения |
| Service Worker, Cache API, Intl, History API | Достаточно для одной оболочки, двух языков и фиксированной учебной зоны | Workbox/Serwist и i18n-фреймворк пока не оправданы; добавить при выявленной сложности |
| Vitest, Playwright, pgTAP / local Supabase | Предметные проверки, браузерные сценарии, SQL/RLS | Одни unit-тесты не обнаружат ошибки IndexedDB, service worker и конкурентных транзакций |
| npm, lockfile, ESLint, поддерживаемый Node.js LTS не ниже 22 | Стандартный воспроизводимый проект | Монорепозиторий сейчас не даёт преимуществ |

Совместимые стабильные версии фиксируются при инициализации после утверждения дизайна. Node.js 20 не выбирать: Supabase прекратил его поддержку; [официальное уведомление](https://supabase.com/changelog/45715-deprecation-notice-dropping-support-for-node-js-20). SQL-миграции — источник схемы; типы БД генерируются. ORM, Redux/Zustand, TanStack Query, Realtime и внешняя продуктовая аналитика в первоначальный набор не входят: рабочим данным достаточно одной наблюдаемой локальной БД.

Источники возможностей: [Dexie React](https://dexie.org/docs/Tutorial/React), [shadcn/ui](https://ui.shadcn.com/docs), [Zod](https://zod.dev/), [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers).

## 3. Рабочая область и офлайн-навигация

- Auth: `/login`, `/register`, `/forgot-password`, `/reset-password`, `/auth/confirm` — обычные маршруты Next.js; операции аккаунта требуют сети.
- Одна статическая рабочая оболочка `/app`; URL-параметр выбирает раздел: `/app?view=today`, `subjects`, `tasks`, `planner`, `focus`, `analytics`, `settings`. Выбранная сущность и дата также представлены параметрами.
- Переключение через native History API не запрашивает RSC payload; Back/Forward сохраняются. Для шести офлайн-разделов одна оболочка надёжнее отдельных server pages. Компромисс — query URL и больший клиентский bundle. Это поддерживаемая возможность [Next.js History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api).
- `/app` не читает cookies на сервере и не содержит личных данных в HTML/RSC. Auth proxy не перенаправляет этот статический маршрут. Клиент открывает набор только ранее вошедшего пользователя; серверные запросы авторизуются отдельно. Клиентское скрытие UI не является защитой API.
- Service worker кэширует канонический `/app` без query и необходимые JS/CSS, локальные шрифты, оба словаря. Офлайн GET-навигация `/app?...` получает ту же оболочку. Остальные URL не получают универсальный HTML fallback.
- Все шесть разделов входят в обязательный офлайн-набор ресурсов. Состояние «готово офлайн» появляется после полной установки оболочки и начальных данных. Нельзя рассчитывать лишь на ранее открытые экраны.
- Кэш версионирован по сборке. Новая версия активируется после безопасной остановки Focus и сохранения правок; старые HTML/chunks не смешиваются с новыми. Миграции IndexedDB и sync-протокол проверяются до отправки очереди.
- API, auth callbacks, экспорты и персональные ответы никогда не кэшируются service worker. Production build отдельно проверяется через reload без сети.

Установка PWA и push после закрытия браузера остаются вне MVP. Service worker для офлайна нужен уже сейчас. [Next.js: PWA и service worker](https://nextjs.org/docs/app/guides/progressive-web-apps).

## 4. Логическая схема данных

Это проект схемы, а не исполняемая миграция. Идентификаторы — UUID, создаваемые на устройстве. Владение задаётся серверной идентичностью, не полем из HTTP.

У изменяемых учебных записей: `id`, `user_id`, `version bigint`, `created_at`, `updated_at`. Канонические timestamps/версии задаёт сервер. Bigint передаётся в JSON десятичной строкой. Архивируемые записи имеют `archived_at`.

| Таблица | Основные поля и связи |
| --- | --- |
| `auth.users` | Управляет Supabase; свои пароли не храним |
| `profiles` | `user_id` PK → auth.users, `locale: ru/en`, настройки Pomodoro; изменяемые поля ограничены |
| `subjects` | `title`, `position`, `archived_at` |
| `topics` | `subject_id`, `title`, `position`, `status: not_started/learning/practicing/mastered`, `archived_at` |
| `tasks` | `subject_id`, `topic_id?`, `title`, `description`, `priority?: low/normal/high`, `due_on date?`, `estimated_minutes?`, `completed_at?`, `archived_at` |
| `subtasks` | `task_id`, `title`, `position`, `completed_at?`, `deleted_at?`; один уровень |
| `study_sessions` | `subject_id`, `topic_id?`, `task_id?`, `title`, `description`, `planned_start_at timestamptz`, `planned_minutes`, `cancelled_at?`, `archived_at` |
| `session_results` | `session_id UNIQUE`, `state: in_progress/completed/discarded`, `rating?: easy/normal/difficult`, `notes`, `timer_mode`, `completed_at?`; один результат на занятие |
| `study_intervals` | `result_id`, `started_at`, `ended_at?`, `source: timer/manual`, `review_state: pending_confirmation/confirmed/conflicted/discarded` |
| `sync_conflicts` | `kind: entity_version/time_overlap`, ссылка на запись/участников, `base_version`, неизменяемые снимки базовой/входящей/серверной версий, `status`, решение, даты |

Служебные таблицы в неэкспонируемой схеме `private`:

| Таблица | Назначение |
| --- | --- |
| `account_state` | `user_id` PK → auth.users, `status: active/deleting`, `revision bigint`; строка блокировки операций аккаунта |
| `mutation_receipts` | `(user_id, mutation_id)` UNIQUE, hash содержимого, результат/конфликт и принятая версия |
| `focus_state` | `user_id` PK, `active_result_id?`, `owner_device_id?`, `generation bigint`; один Focus онлайн |
| `deletion_requests` | Одноразовое задание удаления, этап, допуск повторной авторизации, сроки, коды ошибок; временно переживает auth.users, без учебного содержимого |

Связи и инварианты:

1. Topic принадлежит Subject. Task и Session имеют один Subject и необязательную Topic того же предмета. Если выбрана Task, предмет совпадает; при наличии темы у Task занятие наследует её, иначе может уточнить тему в пределах предмета. Несовместимое изменение предмета блокируется до явного исправления связей.
2. FK включают `user_id`: `(user_id, subject_id)`, `(user_id, task_id)` и аналогичные. Нельзя связать запись с чужой по известному UUID. Проверка принадлежности предмету — составной ключ или транзакционная проверка.
3. Подзадача не ссылается на подзадачу. Завершение всех подзадач/Focus не закрывает Task; время и оценка не меняют Topic автоматически.
4. Плановая длительность/оценка положительны; строки имеют пределы длины. Дедлайн — дата, не момент времени; просрочка начинается со следующего учебного дня.
5. Закрытый интервал: `ended_at > started_at`; confirmed всегда закрыт. Подтверждённые интервалы аккаунта не пересекаются: проверка в транзакции под общей account-блокировкой. Соседние интервалы `[start,end)` допустимы.
6. У результата не больше одного открытого интервала. Finish закрывает интервалы и результат атомарно. Нельзя завершить результат с неподтверждённым временем. Повторная работа после completed — новая Session; незавершённую продолжают.
7. Обычная синхронизация физически не удаляет учебные записи: архив и tombstone подзадачи сохраняются для старых офлайн-устройств. Удаление аккаунта каскадно очищает учебные записи, конфликты и receipts.
8. Архив сохраняет историю и исключает предмет/тему и зависимые записи из текущего планирования. Перед действием показываются затронутые открытые задачи/занятия; фиктивных завершений/отмен не происходит. Экран и восстановление уточняются в дизайне.
9. Индексы: уникальные ключи владения, все FK-пути, `tasks(user_id,due_on)`, `study_sessions(user_id,planned_start_at)`, `study_intervals(user_id,started_at)`, открытые конфликты по `user_id/status`. Остальные — после измерений query plan.

Правила сохранения обязательны в БД даже при клиентской проверке. Подтверждённые поля заметок/названия, исходный план и ссылки сохраняются в истории; изменение пользовательского расписания не переписывает фактические интервалы. Число секунд, освоение и аналитические итоги не дублируются в независимо изменяемых summary-таблицах.

## 5. Протокол синхронизации

Для личного MVP: отправка небольших пачек команд; полный согласованный снимок аккаунта только при изменении `account_state.revision`. Без timestamp-cursor, CRDT, event sourcing и молчаливого last-write-wins. Полный снимок проще корректно применить со связями/архивом; цена — трафик пропорционален истории.

Локально сохраняются канонический снимок/revision, рабочие строки с правками, outbox, конфликты и checkpoints Focus. Outbox содержит `mutation_id`, тип команды, UUID, `expected_version`, базовый снимок, payload, локальную последовательность и зависимости. Паролей/токенов в этих таблицах нет.

Порядок:

1. Локальная валидация → одна Dexie-транзакция: запись и outbox. UI подтверждает локальное сохранение только после commit, не выдаёт его за синхронизацию.
2. Один отправитель на браузер/аккаунт через Web Locks; BroadcastChannel уведомляет вкладки. Это не заменяет серверную блокировку между устройствами. [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).
3. Запуск, возврат во вкладку, восстановление доступа к API, ручная команда и debounce после записи инициируют sync. В видимой онлайн-вкладке revision проверяется примерно раз в 30 секунд. Retry — backoff с jitter; navigator.onLine не доказывает доступность API. Фоновая отправка в закрытом браузере не требуется.
4. POST содержит `protocol_version`, последнюю revision, не более 50 команд и 256 KiB входного JSON. Отправленный payload неизменяем; правка в полёте получает новую локальную генерацию.
5. Next проверяет auth, Origin, JSON и размер; вызывает RPC с пользовательским JWT. RPC повторно проверяет идентичность/живую сессию/аккаунт и блокирует account_state пользователя.
6. Связанные команды выполняются по зависимостям Subject → Topic → Task → Session → Result/Intervals. Многострочный Finish — одна атомарная команда. Зависимости конфликтующего родителя откладываются.
7. Create ожидает отсутствие UUID; update — совпадение expected_version. Успех увеличивает версию. Повтор mutation_id с тем же hash возвращает receipt, с другим payload — protocol error. Короткого TTL у receipts нет, пока допускаются давно офлайн-устройства.
8. При несовпадении версии каноническая запись не меняется: сервер сохраняет базовый, входящий и текущий варианты в sync_conflicts и receipt со статусом conflict. Ошибка прав/ссылок не удаляет локальный вариант. Независимые валидные команды пачки могут быть приняты; ответ описывает каждую. Неожиданная SQL-ошибка откатывает транзакцию целиком.
9. При изменениях увеличивается account revision. Пока удерживается account-блокировка, RPC собирает согласованный снимок. Ту же блокировку используют все изменяющие RPC, Focus, экспорт и начало удаления. Пустой запрос с прежней revision возвращает no change. Порядок не зависит от часов устройства или последовательности незафиксированных транзакций.
10. Одна Dexie-транзакция применяет снимок/receipts/конфликты, убирает только подтверждённые команды и накладывает оставшиеся локальные правки. Старый ответ не затирает новую локальную генерацию. Следующая правка той же записи отправляется после ответа предыдущей; её база обновляется на принятую версию без потери нового payload.

Разрешение конфликта — отдельная команда с актуальной ожидаемой версией: выбрать серверный/локальный вариант или вручную итог. Выбор серверного варианта тоже фиксируется. Если версия опять изменилась, решение не применяется молча. Исходные варианты остаются личными данными до удаления аккаунта и входят в экспорт. Архивирование проходит тот же механизм.

Первый снимок строится в одной серверной транзакции; локальная установка также атомарна. Прерванная загрузка не заменяет рабочую копию неполной. Обновление снимка не стирает outbox.

401 сохраняет очередь до входа в тот же аккаунт. 422 показывает ошибку без вечного retry. Несовместимый протокол останавливает отправку до обновления, сохраняя очередь. Только явное подтверждение удаления сервером, а не timeout/истечение JWT, позволяет автоматически очистить копию.

Ограничение: полный снимок растёт вместе с историей. На раннем milestone проверяется годовой набор, размер ответа и время блокировки с двукратным запасом до лимитов выбранного хостинга. Если не проходит, дальнейшая реализация блокируется до согласования дельта-протокола в ADR-004. Нельзя молча обрезать историю, пропускать tombstones или выдавать неполный снимок за полный.

## 6. Focus, время и аналитика

- Start создаёт/возобновляет Session Result и рабочий интервал. Pause закрывает его, Resume открывает следующий; Pomodoro break не учебный интервал. Finish не меняет Task/Topic.
- Онлайн Start атомарно занимает focus_state под account-блокировкой. При активном результате предлагается продолжить его. Явное продолжение на другом устройстве увеличивает generation; прежний владелец не может незаметно отправить поздний Finish.
- Блокировка не истекает по heartbeat: иначе два онлайн-клиента могли бы считать себя активными. В том же браузере дополнительно действует Web Locks. При недоступном сервере запуск помечается предварительным офлайн, а не успешным онлайн.
- Офлайн-запуск разрешён. При связи независимые интервалы и старое поколение проверяются; конфликт не превращается молча в два активных Focus. На сервере одновременно только один active_result.
- Длительность — границы интервалов, не число setInterval ticks. Монотонное время используется в непрерывной работе; UTC-checkpoints помогают восстановиться. Tick только перерисовывает экран.
- Checkpoint записывается на переходах и периодически. После reload/закрытия/crash неизвестный промежуток от последнего надёжного checkpoint требует подтверждения/коррекции. beforeunload не считается гарантией. Скачок часов и значимое расхождение wall/monotonic elapsed тоже требуют проверки.
- Фоновый экран восстанавливает elapsed при возвращении. Момент звука зависит от браузера; сохранение результата не зависит от своевременного callback. После закрытия браузера сигнал/уведомление не гарантируются.
- Ручное время — реальный диапазон начала/конца с source=manual. Оно не добавляется к duration без проверки пересечений; ошибочный диапазон редактируется явно.
- Пересечение фактических интервалов сохраняет кандидатов, переводит всех участников в conflicted и исключает их из итогов до выбора/обрезки/отклонения. Подтверждение итоговых непересекающихся диапазонов атомарно.
- Подтверждённые итоги суммируют confirmed-интервалы завершённых результатов. Время активного Focus отдельно обозначается предварительным. Паузы, discarded, pending и конфликты не попадают в подтверждённый итог; source=manual виден.
- UTC — в timestamptz; учебная зона — Europe/Ulyanovsk (UTC+4 для текущего требования), не timezone устройства. Date-only дедлайны не переводятся в UTC. Интервал через полночь разрезается по учебным дням; неделя с понедельника. Intl форматирует ru/en, 24 часа; локализованные даты не разбираются через Date.parse.

## 7. Auth и авторизация

Supabase Auth: email/password, подтверждение email, PKCE для email callbacks/recovery, reset password. Минимум 12 символов; разрешены вставка и менеджеры паролей; лимиты Auth и нейтральные сообщения об email. До реального использования нужен SMTP: встроенный сервис ограничен тестовыми адресами. [Supabase SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

@supabase/ssr управляет cookie-сессиями. Сервер проверяет подписанные claims, для операций аккаунта — актуального пользователя. getSession() сам по себе не подтверждает права. Proxy обновляет cookies там, где нужно, но не закрывает статическую оболочку. Персональные ответы — private/no-store; refresh headers сохраняются. [Supabase Next.js SSR](https://supabase.com/docs/guides/auth/server-side/nextjs).

Учебные таблицы находятся в неэкспонируемой схеме app_data, с RLS; RLS также включён для per-user служебных таблиц private как дополнительная защита. В Data API экспонируется только схема api с фиксированными функциями. У anon/authenticated нет прямых DML-grants: нельзя обойти версии/receipts прямым REST update.

Экспонирование api-схемы, USAGE и EXECUTE grants задаются явно в миграциях, без предположений об автоматическом доступе: [изменение Supabase Data API](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

По умолчанию SQL — SECURITY INVOKER. Для узкого RPC-шлюза нужен SECURITY DEFINER: вызывающий пользователь не должен иметь прямой DML. Владелец функций — отдельная NOLOGIN-роль, не владелец таблиц и без BYPASSRLS; только необходимые права. Политики RLS используют user_id = auth.uid(), USING и WITH CHECK; передача владельца запрещена. RPC дополнительно проверяет пользователя и аккаунт.

Обязательно: пустой search_path, полные имена relations, без dynamic SQL и имён таблиц/колонок из запроса; REVOKE EXECUTE у PUBLIC/anon, точечные grants authenticated на api-функции. Не оставлять владельцем postgres по умолчанию. Private helper проверки auth.sessions/auth.users читает только необходимые поля и не раскрывает их в API. Роли, grants, definer-владелец и RLS — предмет отдельных integration tests и advisors. [Безопасность функций Supabase](https://supabase.com/docs/guides/database/functions).

Каждая data RPC проверяет auth.uid(), принадлежность JWT session_id действующей строке auth.sessions и account_state.status=active. JWT после выхода/удаления может оставаться криптографически действительным до expiry, поэтому одной подписи недостаточно. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions). user_metadata не используется для прав; anonymous sign-in отключён.

Обычные запросы Next используют publishable key + JWT пользователя. Secret/admin key доступен лишь server-only удалению. Cookie endpoints проверяют Origin и JSON Content-Type, CORS не открывается произвольно. SQL повторяет проверки данных, поскольку RPC доступна и в обход HTTP-контракта Next.

Офлайн-доступ — чтение/правка ранее сохранённой копии, не новая серверная авторизация. Истечение JWT офлайн не стирает очередь. В сети требуется действующая сессия; вход в другой аккаунт никогда не отправляет прежнюю очередь от его имени.

## 8. Основные потоки и HTTP

| Endpoint | Назначение |
| --- | --- |
| POST /api/sync | Revision/snapshot или команды, receipts и конфликты |
| POST /api/focus/start | Идемпотентный онлайн-захват результата под той же account-блокировкой |
| POST /api/account/export | Проверка актуального входа и revision-барьера; JSON download/no-store |
| POST /api/account/delete | Свежая повторная авторизация, подтверждение, запуск/продолжение удаления |
| GET /api/account/delete-status | Статус по короткоживущей одноразовой квитанции без доступа к учебным данным |
| POST /api/account/status | Только состояние аккаунта по проверенному доказательству идентичности; не чтение/восстановление учебных данных |
| POST /api/internal/deletions | Только повторы уже подтверждённых deletion requests по отдельному scheduler credential |

Auth использует официальный SDK/callback routes, не свой password backend. Ошибки: стабильный code, ошибки полей, retryability, request id; текст локализуется в UI. Команды — строгий discriminated union, без произвольной записи системных полей.

Первый вход: Auth → проверка существующего подтверждённого пользователя/сессии → идемпотентное создание профиля/account_state → полный снимок → атомарная установка локально → статические ресурсы → ready offline. Старый JWT удалённого пользователя не может создать профиль заново.

Создание плана: локальные Subject/Topic/Task/Session видны сразу, зависимые UUID сохраняются без сети; sync отправляет по связям. Today и Planner читают одну БД. Пропущенность вычисляется из планового конца и отсутствия активного/завершённого результата, а не отдельным cron-переключением статуса; cancelled и архив исключены.

Finish: локальная атомарная команда сохраняет интервалы/результат; сервер проверяет версию, владельца/generation и пересечения, завершает результат и освобождает Focus. Повторный Finish не создаёт дубликат и не меняет самооценку темы.

Экспорт: локальная очередь отправлена, конфликты разрешены → запрос с ожидаемой account revision → под account-блокировкой сервер проверяет revision и отсутствие открытых конфликтов → согласованный JSON. Конкурентная правка требует нового барьера. Формат: schema_version, exported_at, timezone, сущности/связи/архив, сохранённые варианты конфликтов. Нет credentials, auth sessions и технических receipts. Неотправленные правки другого offline-устройства не обещаются в выгрузке.

Удаление: Auth проверяет повторный пароль; сервер выдаёт одноразовый короткоживущий допуск, привязанный к пользователю/сессии/операции, без хранения пароля. Под account-блокировкой устанавливается deleting и создаётся deletion_request. С этого commit все обычные RPC блокируются даже со старым JWT. Далее отзыв сессий, server-only Auth Admin delete и каскад данных. Успех показывается после подтверждения удаления; текущие cookies/IndexedDB очищаются. После отзыва сессии ограниченная квитанция позволяет узнать только статус удаления. Она передаётся в Authorization header, хранится сервером как hash и не попадает в URL/логи; ответ no-store.

Auth Admin API и свои SQL-таблицы не составляют одну транзакцию. Процесс идемпотентен; сбой оставляет deleting, а не ложный success. Незавершённые deletion_requests повторяет Supabase Cron: HTTP-вызов /api/internal/deletions примерно раз в пять минут с отдельным server-only credential из Vault. Этот endpoint принимает только уже подтверждённые задания из БД, не произвольный user_id из HTTP; повторно проверяет статус, не хранит пароль и не создаёт новых заданий. Короткие блокировки этапов предотвращают конкурирующую обработку. Это один узкий повтор, не общая очередь/workflow. [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart). При повторном входе deleting-аккаунт может только продолжить удаление. Квитанции/задания очищаются после завершения и короткого периода получения статуса; срок и backup retention фиксируются до production. [Ограничение удаления JWT](https://supabase.com/docs/guides/auth/managing-user-data).

Старое устройство после достоверного account_deleted очищает копию. Истёкший JWT/неудачный refresh не доказывает удаление: копия блокируется до подтверждения идентичности, а не уничтожается из-за ошибки сети. Endpoint статуса не принимает произвольный email как доказательство и не выдаёт учебные данные. При ещё действующей подписанной идентичности отсутствие account/auth user даёт account_deleted; после полного истечения доказательства требуется повторная проверка владения или явная локальная очистка. Дистанционно гарантировать стирание навсегда отключённого устройства невозможно; это документированное ограничение FR-10.

## 10. Безопасность и эксплуатация

- TLS, server-only secrets, RLS, минимальные роли, отсутствие персонального CDN-кэша. Секретов нет в NEXT_PUBLIC_, export или логах. Scheduler credential хранится в Supabase Vault и env сервера, не в cron SQL/history в открытом виде.
- Заметки — plain text; безопасный React-вывод, CSP, локальные ресурсы. IndexedDB не защищает от XSS/доступа к профилю браузера. Шифрование с ключом рядом с данными не решает эту угрозу.
- Локальная БД разделена по user_id. Logout останавливает отправителей, уведомляет вкладки и очищает копию. Перед очисткой несинхронизированного — выбор синхронизировать или явно отказаться от него; ошибка сети сама ничего не удаляет.
- Persistent storage запрашивается при доступности; quota/write errors видны. Очистка браузера может уничтожить неотправленные данные; абсолютная сохранность не обещается. [Browser storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).
- Auth callback allowlist, без произвольных next URL; Secure/SameSite по контракту SDK. Не обещать HttpOnly для cookies, которые читает официальный browser client.
- Лимиты JSON/строк/пачек, таймауты, rate limits; нет присваивания служебных полей из payload. Прямой RPC проходит те же обязательные проверки, что Next endpoint.
- Технические логи: request id, код ошибки, sync/RPC duration, snapshot bytes, backlog; без заметок, email, JWT и паролей. Сторонняя продуктовая телеметрия не добавляется.
- Local/test и production разделены. Источник схемы — SQL-миграции. Восстановление backup проверяется до production-использования.
- Хостинг: managed Node.js с HTTPS + managed Supabase. Конкретный провайдер/регион/план выбираются при инициализации по бюджету, доступности и лимитам payload. Vercel допустим, но не обязателен; специфичных hosting API в предметной логике нет.
- До production зафиксировать SMTP, backup/deletion retention, лимиты, домен, браузерную матрицу и доступность выбранных сервисов владельцу. Без этого эксплуатационная готовность не заявляется.

## 11. Риски и меры

| Риск | Мера и проверка |
| --- | --- |
| Собственный sync | Узкие команды, один account-lock, receipts/версии, тесты потери ответа и двух устройств |
| Рост полного снимка | Ранний годовой load profile; если не укладывается — согласовать delta-протокол до расширения UI |
| Next RSC / service worker / новая сборка | Статическая рабочая точка входа, production reload без сети, обновление со старой очередью |
| Частичное удаление | Deleting gate, одноразовый допуск, идемпотентные этапы, retry, отсутствие ложного success |
| Единственный Focus при разделении сети | Строгое правило только для подтверждённых онлайн-запусков; offline-предварительность и разбор пересечений |
| Фоновые таймеры/часы/Safari | Интервалы/checkpoints, подтверждение неизвестного времени, реальный Safari smoke test |
| Потеря IndexedDB | Ошибки записи/места видимы, persist по возможности, честный sync-индикатор |
| SQL definer и обход HTTP | Минимальная отдельная роль, RLS/active session в RPC, adversarial integration tests |
| SMTP/план/backup | Настройка и проверка реальных email и восстановления до личного использования |

## 12. Тестирование

1. **Vitest:** статусы и независимость Task/Topic, интервалы [start,end), полночь UTC+4/date-only дедлайны, паузы/rounding/ручное время, наложение локальных правок на новый снимок. Не тестировать копию реализации и декоративные компоненты.
2. **pgTAP + local Supabase:** чужие UUID/FK, anonymous, смена user_id, system fields, grants/RLS, отозванный session_id, receipt/hash, версии, атомарный Finish. Конкурентные Focus/экспорт/удаление — реальными параллельными запросами через integration harness.
3. **Playwright на production build:** signup/recovery через локальный email inbox; create → plan → Focus → review → history; два browser contexts; обрыв после commit до receipt, retry, конфликт и третья правка во время его разрешения, правка в полёте запроса, offline reload всех разделов, обновление с outbox.
4. **Export/delete:** JSON сохраняет связи/архив, не секреты; открытый конфликт блокирует export; сбой Admin API оставляет deleting и retry завершает; старый токен не читает/пишет, offline-копия не воскрешает аккаунт; signup тем же email получает другой user_id.
5. **UI/accessibility:** desktop/mobile, ru/en, длинные названия, пустые/ошибочные/offline/conflict-состояния, клавиатура, ручная screen reader проверка и axe критического пути. Chromium/Firefox/WebKit CI; реальный iOS Safari перед релизом.
6. **CI:** lockfile install, lint, tsc, unit, SQL/integration, production build, критические E2E. Screenshot baselines только после утверждения дизайна. Процент coverage не подменяет критерии PRD.

Начальная матрица: актуальные стабильные Chrome/Edge/Firefox/Safari desktop, Safari iOS и Chrome Android; минимальные версии фиксируются после проверки IndexedDB, Web Locks, Service Worker. Неподдерживаемое API не заменяется небезопасной гарантией.
