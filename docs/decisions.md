# StudyFlow — журнал архитектурных решений

Status: **Approved**. The user explicitly approved architecture 1.0 and ADR-001–ADR-010 before starting Stage 3. Update the relevant ADR if a technical decision changes; design work must respect these approved boundaries.

## ADR-001. Одно Next.js-приложение и Supabase

**Решение:** App Router + strict TypeScript; Supabase Postgres/Auth; Route Handlers для HTTP. Один deploy приложения и одна БД.

**Почему:** нужны UI, готовый password auth, связанные данные и транзакции; отдельный backend преимуществ пока не даёт.

**Альтернативы:** Vite SPA с serverless endpoints; отдельный Node API; Firebase.

**Компромисс:** Next богаче необходимого клиентскому UI; Supabase создаёт зависимость от Auth/RLS/RPC. Не добавлять микросервисы, ORM и универсальные repositories.

## ADR-002. Локальная БД для рабочих данных

**Решение:** Dexie/IndexedDB, наблюдаемые запросы; атомарная запись данных и outbox. Сервер хранит подтверждённую версию; клиент — рабочую копию с неподтверждёнными правками.

**Почему:** офлайн включает редактирование и Focus, не только чтение кэша.

**Альтернативы:** нативный IndexedDB, онлайн-CRUD с HTTP-кэшем, PowerSync/Dexie Cloud.

**Компромисс:** свои локальные миграции/retry/конфликты. Готовый sync-продукт сокращает часть кода, но добавляет инфраструктуру/провайдера и не устраняет предметные конфликты времени. Не заводить второй рабочий кэш в TanStack Query/глобальном state store.

## ADR-003. Одна статическая рабочая оболочка

**Решение:** /app?view=..., native History API и service worker для общей оболочки/обязательных ресурсов.

**Почему:** offline reload и любой раздел не должны зависеть от серверного RSC-запроса и персонального SSR-кэша.

**Альтернативы:** отдельные App Router pages с кэшированием HTML/RSC; отдельная Vite SPA.

**Компромисс:** query URL, клиентский UI и больший начальный bundle. Auth и HTTP остаются обычными routes. Установка PWA не требуется. Если дизайн докажет необходимость других routes, пересмотреть до реализации, не смешивать стратегии.

## ADR-004. Версии, receipts и полный снимок

**Решение:** команды mutation_id/expected_version, per-user row lock, account revision, полный согласованный снимок при изменениях.

**Почему:** атомарность, порядок и retry без дублей не зависят от часов. Для личного MVP проще commit-ordered change log с пагинацией.

**Альтернативы:** timestamp sync, delta log, CRDT, last-write-wins.

**Компромисс:** трафик/сборка снимка растут с историей; операции одного аккаунта кратко сериализованы. Обязателен ранний годовой профиль; если бюджет не пройден — согласовать delta-протокол. Клиентский updated_at не надёжный cursor.

## ADR-005. Долговечные явные конфликты

**Решение:** базовый, входящий и серверный варианты сохраняются; итог выбирается с актуальной expected_version. Новые локальные правки не теряются при применении снимка.

**Почему:** PRD запрещает молча терять независимые правки; пересекающееся фактическое время нельзя просто складывать.

**Альтернативы:** field merge, last-write-wins, ручное восстановление вне приложения.

**Компромисс:** отдельный UI и записи конфликтов, иногда необходим выбор пользователя. Снимки — личные данные, удаляются вместе с аккаунтом. CRDT не решает, были ли два пересекающихся занятия реальной учёбой.

## ADR-006. SQL и узкий RPC-доступ

**Решение:** нормализованные таблицы, user_id/FK/версии/RLS; нет прямого клиентского DML. Малый фиксированный набор транзакционных RPC с отдельной ограниченной NOLOGIN definer-ролью, не postgres и не BYPASSRLS.

**Почему:** версия, receipt, ссылки и блокировка — одна транзакция; прямой Data API не должен обходить sync-протокол.

**Альтернативы:** прямой Supabase CRUD; server-only Postgres connection с ручным JWT context; ORM и отдельный backend.

**Компромисс:** критические правила сохранения написаны на SQL, роли/grants требуют review. TypeScript содержит предметные расчёты; БД — инварианты сохранения. Это не универсальный CRUD-конструктор.

## ADR-007. Готовый Auth и живая сессия

**Решение:** Supabase email/password, confirmation/recovery, @supabase/ssr; session_id и активный аккаунт проверяются внутри data RPC. Admin key — только server-only удаление.

**Почему:** JWT-подпись не доказывает, что сессия и аккаунт ещё действуют; старое устройство не должно восстановить удалённые данные.

**Альтернативы:** свой auth, Clerk/Auth0, только JWT до expiry.

**Компромисс:** проверка состояния и SMTP требуют настройки. Офлайн работает с сохранённой копией, но новой серверной авторизации без сети нет. Cookie-параметры следуют SDK, не выдуманному HttpOnly-режиму.

## ADR-008. Интервалы и явный владелец Focus

**Решение:** план отдельно от результата и timer/manual-интервалов; reload требует подтверждения неизвестного времени. Онлайн — один active_result; смена устройства увеличивает generation, блокировка не истекает молча.

**Почему:** фоновые ограничения и два офлайн-устройства исключают надёжность tick-counter/клиентского singleton.

**Альтернативы:** хранить только duration, серверный таймер, heartbeat lease с автоматическим истечением.

**Компромисс:** больше записей, восстановление и разбор пересечений. Строгая единственность только для подтверждённых онлайн-запусков; при разделении сети нужен последующий выбор. Точный фоновый сигнал не обещается.

## ADR-009. Отдельные операции экспорта и удаления

**Решение:** online JSON под revision-барьером; reauth → deleting gate → отзыв сессий → Auth delete/cascade → очистка копии. Небольшое deletion request и повтор этапов через Supabase Cron → защищённый Next endpoint; credential в Vault/env.

**Почему:** Auth Admin API и SQL не являются одной транзакцией; удаление должно переживать частичный сбой.

**Альтернативы:** прямой deleteUser без gate, SQL-транзакция с внешним HTTP, общая очередь/workflow.

**Компромисс:** узкий механизм повторов и одноразовые квитанции, но нет отдельного оркестратора. Успех только после проверки; полностью офлайн-устройство дистанционно не стереть. Backup retention фиксируется до production.

## ADR-010. Минимальные UI и инструменты проверки

**Решение:** Tailwind + отдельные shadcn primitives, typed ru/en словари, Intl, фиксированная учебная зона UTC+4. Planner день/неделя — сетка и доступная форма создания/переноса без обязательного drag-and-drop. Аналитика — таблицы/простые SVG с текстовой альтернативой. Vitest + SQL/integration + Playwright.

**Почему:** PRD не требует сложного календарного движка и chart package; важнее цельный сценарий и утверждённый дизайн.

**Альтернативы:** FullCalendar, dashboard UI kit, i18n-framework, chart library.

**Компромисс:** нет готовых drag/resize, advanced charts и сложных calendar layouts. Если дизайн потребует их, отдельно оценить библиотеку и доступность. Не писать тесты только ради coverage.

## Актуальность источников

Использованы официальные Next.js, Supabase, Dexie, Zod, shadcn/ui и browser docs; ссылки на фактические ограничения находятся в architecture.md. Markdown changelog Supabase не поддерживается web-инструментом, поэтому просмотрена [HTML-версия](https://supabase.com/changelog). Перед установкой повторно проверить совместимость версий и security advisories. Предложения архитектуры не требуют настройки сервисов на этом этапе.
